## Goal

Make sure tasks get finished instead of put off. Tasks have no due dates. Each task sits in one of four priority quadrants and has a position within it. The top-left quadrant, **Next version**, is the checklist of everything to finish before the user's next release. The user deploys by hand, at least once a week, and Gravity knows nothing about deployments. When the user asks, an LLM plans the next version over MCP: it completes tasks whose issues closed, takes stale work out, and adds every urgent GitHub issue plus the next slice of each repo's version milestone.

## Non-goals (v1)

Login or any other auth · a history or event log · due dates · a REST API · scheduled or automatic triage · drag-and-drop · multiple users · the app talking to GitHub itself · a theme toggle · a UI for dropped tasks · automated backups · a record of deployments or releases.

## Architecture

One Next.js 16 app in one Docker container.

- **UI**: a single server-rendered page at `/`. Every change (add, complete, move, edit, drop) is a Server Action.
- **MCP**: a route handler at `/mcp` that speaks MCP over Streamable HTTP, **stateless** (no session state between calls). It uses the official MCP TypeScript SDK's web-standard transport; the implementation plan picks the exact package after checking current versions.
- **Task module** (`lib/tasks`): the only code that reads or writes tasks. Server Actions and MCP tools both call it, so every rule below is enforced in exactly one place.
- **Storage**: SQLite through Node's built-in `node:sqlite`. No ORM and no native module. WAL mode.
- **Clock**: the task module receives the current time as a dependency, so tests can control it.

## Data model

Timestamps are ISO-8601 UTC strings.

### `tasks`

| column | type | rule |
|---|---|---|
| `id` | INTEGER PK | |
| `description` | TEXT NOT NULL | trimmed, 1–200 characters, no newlines |
| `quadrant` | INTEGER NOT NULL | 1–4 (see Quadrants) |
| `position` | INTEGER NOT NULL | order within the quadrant among open tasks; 0 is the top |
| `issue_url` | TEXT NULL UNIQUE | must match `^https://github\.com/[^/]+/[^/]+/issues/\d+$` |
| `created_at` | TEXT NOT NULL | set once, never changed |
| `completed_at` | TEXT NULL | "is done" is `completed_at IS NOT NULL`; there is no separate flag |
| `dropped_at` | TEXT NULL | the task was abandoned on purpose |
| `q1_since` | TEXT NULL | when the task last entered quadrant 1; null outside quadrant 1 |
| `demotions` | INTEGER NOT NULL DEFAULT 0 | how many times the task moved to a lower-priority quadrant (rule 7) |

A task is **open** when both `completed_at` and `dropped_at` are null. At most one of them is set.

There is no history or event log: `tasks` is the only table.

### Migrations

Numbered SQL steps run at startup, tracked with `PRAGMA user_version`.

## Quadrants

| # | name | place on a wide screen |
|---|---|---|
| 1 | Next version | top-left |
| 2 | Schedule | top-right |
| 3 | Delegate | bottom-left |
| 4 | Later | bottom-right |

Priority runs 1 > 2 > 3 > 4. **Up** means a lower quadrant number and **down** means a higher one. Within a quadrant, a lower `position` ranks higher.

## Rules

1. **Positions** stay contiguous (`0..n-1`) among the open tasks in each quadrant after every change.
2. **Add**: the new task goes to the bottom of its quadrant unless a `position` is given, in which case it is inserted there and the tasks below shift down.
3. **Duplicate issues**: adding a task whose `issue_url` already exists, in any state, returns the existing task with `existing: true` and changes nothing.
4. **Quadrant 1 clock**: entering quadrant 1, by add or by move, sets `q1_since = now`. Leaving quadrant 1 clears it. Completing, dropping and reopening do not change it.
5. **Local dates** use the timezone in `APP_TZ` (default `Asia/Jakarta`). The **carry-over** of an open quadrant-1 task is the number of local days from the date of `q1_since` to today: how long it has been in Next version. The badge shows nothing below `VERSION_AMBER_DAYS`, amber from `VERSION_AMBER_DAYS` up to `VERSION_STALE_DAYS`, and red at `VERSION_STALE_DAYS` or more (with today's values: nothing at 0–4, amber at 5–6, red at 7+). Nothing runs at midnight; carry-over is computed when read.
6. **Age** of a task is the number of local days from the date of `created_at` to today.
7. **Demotions**: every move to a higher-numbered quadrant adds 1 to `demotions`. It never goes down.
8. **Move** to another quadrant puts the task at the bottom of the target quadrant unless a `position` is given. Moving to the quadrant the task is already in requires a `position` and only reorders it. Moving up from quadrant 1 or down from quadrant 4 is rejected.
9. **Complete** sets `completed_at`. **Drop** sets `dropped_at`. Both remove the task from its quadrant's ordering.
10. **Reopen** clears `completed_at` or `dropped_at` and puts the task at the bottom of its quadrant. `q1_since` is kept, so completing and then reopening a task cannot reset its carry-over.
11. **No delete.** A task leaves the matrix only by being completed or dropped.
12. **Closed tasks** (completed or dropped) can only be reopened. Editing, moving, reordering, completing or dropping them is rejected.
13. **Visibility limits** live as constants in one file. Quadrant 1 always shows every open task and shows no warning, however many there are. Quadrants 2–4 show their top 5 (`VISIBLE_PER_QUADRANT = 5`) followed by a "+N more" toggle that shows the rest in place. The toggle state lives only in the browser and is not saved.

## UI

### Layout

- **Width ≥ 768px**: a 2×2 grid laid out as in the Quadrants table. Quadrant 1 has the strongest visual weight.
- **Width < 768px**: one vertical column in the order 1, 2, 3, 4. Each quadrant header sticks to the top while its quadrant scrolls past. Tap targets are at least 44px. The page never scrolls horizontally.
- **Summary line** at the top: `Next version N open · S over a week · oldest open Dd`.
  - N = the number of open quadrant-1 tasks.
  - S = open quadrant-1 tasks with a carry-over of `VERSION_STALE_DAYS` (7) or more.
  - D = the largest age among open tasks. The `oldest open` part is left out when nothing is open.
- **Quadrant header**: the name, the open count, and "+N more" when tasks are hidden.
- **Done today**: a list below the matrix of tasks completed today, each with its completion time and an **undo** button that reopens it. Dropped tasks are not listed.

### Task row

- A checkbox completes the task. The row updates immediately and the server catches up afterwards.
- The description; clicking it edits it in place.
- Badges:
  - days in Next version (quadrant 1 only, amber or red), e.g. `5d in version`
  - age, e.g. `12d`
  - demotions, e.g. `↓2`, only when above 0
  - `repo#123` linking to `issue_url`, only when it is set
- A **⋯ menu** that opens inline below the row (not a pop-up) with: move up a quadrant · move down a quadrant · move to quadrant… · up within quadrant · down within quadrant · drop. Drop asks for confirmation inline (the button turns into **Confirm drop**), since the UI has no undo for it.
- Each quadrant ends with a one-line **Add task** input. Pressing Enter adds the task to the bottom of that quadrant.

### Behaviour

- When the tab becomes visible again (`visibilitychange`), the page re-renders from the server, so changes the LLM made over MCP appear.
- Light and dark themes follow the system setting through Tailwind's `dark:` media variant. There is no toggle and no theme library.
- Components: `Quadrant`, `TaskRow`, `AddTask`, `Badge`, `TaskMenu`. Plain Tailwind, no component library.
- Font: Mona Sans (`/home/jin/HomeLab/kolva-gravity/ui/Mona-Sans.var.woff2`, from a Tailwind template in the main checkout's untracked `ui/` folder) loaded through `next/font/local`. Nothing else from `ui/` is used, and `ui/` is never committed.
- Everything is keyboard-reachable. The checkbox is a real `<input type="checkbox">`, and menu items are `<button>`s with accessible labels.

## MCP

### Endpoint and client config

`POST https://gravity.local.zeven.day/mcp`. Because the server is stateless, `GET` and `DELETE` return 405. There is no auth; anyone on the LAN or the WireGuard VPN can call it, which is an accepted risk.

```json
{ "mcpServers": { "gravity": { "type": "http", "url": "https://gravity.local.zeven.day/mcp" } } }
```

For Claude Code: `claude mcp add --transport http --scope user gravity https://gravity.local.zeven.day/mcp`

### Tools

Every tool calls the task module. Inputs are validated with zod. A broken rule or an unknown id returns a tool result with `isError: true` and a message that says what is needed, e.g. `task 12 is completed; reopen it first`.

| tool | input | output |
|---|---|---|
| `get_matrix` | `quadrant?` | every open task, with **no** visibility limit: `id, quadrant, position, description, issue_url, age_days, carry_over_days, demotions, created_at` |
| `add_task` | `description, quadrant, issue_url?, position?` | the task, plus `existing: true` when the issue was already a task |
| `update_task` | `id, description` | the task |
| `move_task` | `id, quadrant, position?` | the task |
| `reorder_quadrant` | `quadrant, ids[]` | the quadrant's new order. `ids` must be exactly the open tasks in that quadrant, otherwise it is an error |
| `complete_task` | `id` | the task |
| `reopen_task` | `id` | the task |
| `drop_task` | `id` | the task |

To reorder within a quadrant, use `move_task` with the same quadrant and a `position` (rule 8), or `reorder_quadrant` for the whole quadrant at once.

### `triage` prompt

The server exposes an MCP prompt named `triage` with one optional argument, `repos`: a comma-separated list of `owner/repo`. Claude Code shows it as `/mcp__gravity__triage`. The text lives in the repo (`lib/mcp/triage.md`), and `triagePrompt` fills its `{{repos}}`, `{{budget}}` (`VERSION_BUDGET` = 10) and `{{stale_days}}` (`VERSION_STALE_DAYS` = 7) placeholders. The full step-by-step behaviour is specified in `docs/specs/2026-10-09-next-version.md`; in short, the prompt states that an issue is exactly one task and that triage only reads GitHub, defines urgency, points (`size:S` 1, `size:M` 2, `size:L` 4, otherwise 2) and the budget, and tells the LLM to:

1. Call `get_matrix`.
2. Complete each task whose issue is closed (`gh issue view`).
3. Deal with every quadrant-1 task at `VERSION_STALE_DAYS` or more: urgent stays; non-urgent with an `issue_url` moves to quadrant 2, never split; without one, split or move down.
4. Move put-off tasks in quadrants 3 and 4 up one quadrant, never into quadrant 1.
5. If `repos` is given, add every urgent issue regardless of the budget, then roadmap issues from each repo's earliest open version milestone, in dependency order and in turns across the repos, while quadrant 1's points stay within the budget. Rely on `add_task` returning the existing task to avoid duplicates.
6. Top up from quadrant 2 while the budget allows.
7. Reorder each quadrant with `reorder_quadrant`.
8. Finish with a short summary, including points used.

## Deploy

- **Port**: `portctl claim gravity --host 30 --container-port 3000`, then `portctl generate`. Traefik terminates TLS for `gravity.local.zeven.day` and forwards to `http://192.168.7.30:<claimed port>`.
- **`compose.yaml`**: a single service `gravity`, `build: .`, `restart: unless-stopped`.
  - `ports: ["<claimed port>:3000"]`, with a comment saying the port was claimed with portctl (the same pattern as the kolva-sim services).
  - Volume `./data:/data`; `/data/` is added to `.gitignore`.
  - Environment: `DATABASE_PATH=/data/gravity.db`, `APP_TZ=Asia/Jakarta`.
- **Dockerfile**: a multi-stage build on Node 24 LTS (`node:24-slim`) with pnpm through corepack, `next.config.ts` set to `output: 'standalone'`. The runtime runs `node server.js` as a non-root user. The healthcheck uses `GET /` through Node's `fetch`, since the slim image has no curl.
- **README**: how to deploy, the MCP one-liner, and how to back up (copy `data/gravity.db`).

## Testing

- **Unit (Vitest)**: the task module against an in-memory database with a fixed clock. Rules 1–12 each have at least one test, including carry-over across a WIB midnight.
- **MCP integration (Vitest)**: an MCP SDK client calls the `/mcp` handler and exercises every tool and the `triage` prompt listing. Broken rules come back as `isError` results.
- **E2E (Playwright)**: one spec run at 375px and 1280px wide covering add, complete, undo, move, and drop with its confirmation, and checking that the 375px page has no horizontal scroll.
- **Deploy check**: `https://gravity.local.zeven.day` returns 200, and `claude mcp list` shows `gravity` as connected.
